# 系統分析輔助

**規劃**。工作名稱；正式品牌待定。本線代號 **P3（系統分析輔助）**。獨立 Web 產品，**不是**仲介發案精靈，也**不是**控制台需求工作台的雲端版，也**不是**模啟「系統分析者控制台」。

**代號撞車：** 模啟自己的「P3」＝第二產業超薄包，與本線「P3 系統分析輔助」不同。對外與文件必須寫全名，禁止兩邊都簡稱「P3」卻不標產品。

衝突時以 [總規格・四套產品](spec.md#四套產品) 為準。開門後才允許啟動 [仲介平台](marketplace.md)（P4）。

## 要解決的問題

有軟體／資訊需求的人，多半能說「痛點與期望」，但寫不出需求文件、規格、可指派的 Issue。現有文件把這段塞進仲介「網頁精靈」，等於用媒合 UI 假裝系統分析——那是規劃跑掉的原因之一。

本產品以**系統分析為核心**，用 AI 輔助把：

**需求概念 → 需求文件 → 規格文件 → 可追蹤 Issue**（含測試、debug、驗收工作項）

並讓使用 AI_Project 控制台的工程師**收得到指派**。

## 給誰

| 角色 | 工作 |
|------|------|
| 需求窗口／PO | 用口語與素材描述問題；確認產出的需求與範圍 |
| 系統分析／PM | 審查需求文件與規格；調整優先序與驗收 |
| Tech Lead | 確認技術可行性與拆 Issue 粒度 |
| 工程師 | 在控制台／GitHub 收到指派後開工（不在本站寫碼） |

## 過程（能力，非實作）

```mermaid
flowchart LR
  Concept[概念與素材]
  ReqDoc[需求文件]
  SpecDoc[規格文件]
  Track[可追蹤Issue]
  Assign[指派工程師]
  Concept --> ReqDoc
  ReqDoc --> SpecDoc
  SpecDoc --> Track
  Track --> Assign
```

1. **概念**：訪談式引導、上傳既有簡報／信件／畫面；標出假設與待決問題。
2. **需求文件**：問題、干係人、範圍／非範圍、驗收條件、優先序。過程對齊 **ISO/IEC/IEEE 29148** 的需求工程概念，不假裝已認證合規。
3. **規格文件**：行為規格、介面約束、資料與非功能需求；可匯出 Markdown／JSON。語意可對映 **OMG ReqIF**／**OSLC RM**；第一刀**不**做完整 ReqIF 伺服器。
4. **可追蹤 Issue**：拆成 GitHub Issue（或同等工作項），帶驗收、標籤、依賴；含測試與 debug／缺陷類工作項。語意對齊 **OSLC Change Management**；傳輸以 GitHub 為準。
5. **指派**：寫回 GitHub assignee／專案板；控制台經 GitHub 與「我的派工」看得到。可選把專案範圍摘要送到公司工作區。

## 與其他產品的邊界

| 產品 | 本站做 | 本站不做 |
|------|--------|----------|
| 控制台 | 產出 Issue 讓工程師接收 | 本機編譯、工時真相、Agent |
| 公司工作區 | 可選同步專案／範圍 | 薪資、毛利、戰情室、公開回報入帳 |
| 仲介 | 驗證成功後才允許仲介依賴本能力 | 會員認證、合同、抽成、媒合瀏覽 |
| 模啟（姊妹產品） | 方法論借鏡；後期可選文件契約 | 合併安裝／登入／DB；嵌進四套角色台 |

控制台既有「需求工作台／進件」維持**現況**給已在倉內的團隊。本站服務「還沒有清楚 Issue」的上游分析。

## 與模啟・系統分析者控制台

模啟分析者台是**已出貨**的熱加入第一閘（客戶／產業／方案 → module-definition／變體 → `needs-assignment` Issue）。本站是**規劃中**的汎用「概念 → 需求 → 規格 → 可指派 Issue」。相關但不同層，**現在不做產品／API／安裝串連**（維持 L0 敘事＋L1 薄契約）。

| | 模啟・系統分析者控制台 | 本線・系統分析輔助 |
|--|------------------------|---------------------|
| 狀態 | 已出貨（Lane A／B／C） | 規劃；未建專案 |
| 服務誰 | SA／模組契約定稿者 | 有資訊需求、不會寫 PRD 的窗口／PM |
| 產出 | `Modules/{MOD}/SA/`、definition、變體、GitHub Issue | 需求文件 → 規格 → 汎用可指派 Issue |
| 下游 | 模組開發者台 → 熱加入 | 控制台工程師開工；門檻後才開仲介 |
| 第一軸 | 客戶／產業／方案／模組槽 | 任意軟體／資訊需求概念 |

**可借鏡（方法論，非合併程式）：** MD → validate；定稿差異 → Issue；`needs-assignment` 紀律；假設／待決可見；ModuleDesigner.AI 類設計書生成流程。

**禁止：** 把本站做進模啟分析者台或四套角色台；共用安裝包／登入／DbContext；現在為本站開工深整合。若日後要服務「模啟模組開發」路徑，用**適配器**對齊 definition／SA 格式，不搬進本線控制台四套角色台。家族可同倉（見 [架構 AD-29](architecture.md)），仍禁止與模啟 L2 合併。

細節與整合級別見模啟倉 `DocsLibrary/V3/00-產品/與AI_Project_Console整合評估.md`。

## 產物

| 產物 | 形式（第一刀） | 後續可選 |
|------|----------------|----------|
| 需求文件 | Markdown＋結構化 JSON | ReqIF 匯出 |
| 規格文件 | Markdown＋結構化 JSON | OSLC RM 資源 |
| Issue 包 | GitHub Issues（含標籤與 checklist） | 其他追蹤器適配器 |
| 追溯矩陣 | 需求 ID ↔ 規格 ID ↔ Issue | — |

## 對仲介的開門條件（P4 gate）

仲介（P4）不得在下列條件未關閉前當「下一實作」開工：

| # | 條件 | 怎麼驗 |
|---|------|--------|
| G-01 | 非工程師窗口能在本站走完「概念 → 需求文件 → 規格 → Issue」 | 錄影或見證跑一次；產物齊全 |
| G-02 | 指派的工程師能在控制台看到工作項並開工 | 控制台／GitHub 有指派；能 clone／開工 |
| G-03 | 閉環可重複 | 至少 **N=3** 次獨立需求（不同窗口或不同專案）成功 |
| G-04 | 範圍／非範圍寫進產物，且標註 AI 假設 | 審查清單通過 |

N 的數字可在 PRD 調整；未達標則仲介維持「門檻後／不做」。

## 非目標（P3 第一刀）

- 取代控制台或公司工作區
- 取代或合併模啟系統分析者控制台／四套角色台
- 自動媒合工程師報價與成交（那是仲介）
- 完整 ReqIF／OSLC RDF 伺服器
- 代管客戶原始碼
- 勞務派遣
- 現在與模啟做 SSO、共用 DB 或單一安裝包

## 成功長什麼樣

一份口語需求進來，離開時有：可讀的需求文件、可執行的規格摘要、一組已建立並可指派的 Issue；工程師用控制台接到任務後能開工。重複三次後，才討論是否開啟仲介。
