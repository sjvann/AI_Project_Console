## 怎麼跑一輪（標準路徑）

1. 啟動分析站：`dotnet run --project src/AiProject.Analysis.Web`（或 `deploy/analysis` compose）。
2. 非工程師窗口開案：填標題、概念、假設、待決。
3. 產出**需求文件**（含範圍／非範圍／驗收）；下載 Markdown／JSON。
4. 產出**規格摘要**（SPEC 追溯 REQ）；下載 Markdown／JSON。
5. 組 Issue 包 → **發布**（真實 GitHub 或註明 dry-run 僅供預演；**關門須至少一輪真實寫入＋指派**）。
6. 工程師在 GitHub 看到 assignee；以控制台選該 repo／任務面確認可見並能 clone／開工。

預設 `Analysis:GitHub:DryRun=true` 只算預演，**不**計入 G-02／G-03 關門次數。

## G-01 — 概念 → 需求 → 規格 → Issue

**條件：** 非工程師窗口能在本站走完全流程；產物齊全。

| 勾選 | 檢查項 |
|:----:|--------|
| ☐ | 窗口角色非工程師（PO／業務／需求窗口） |
| ☐ | 已開一則分析案（概念＋可見假設） |
| ☐ | 需求文件含：問題、範圍、非範圍、驗收、REQ-ID |
| ☐ | 規格摘要含：SPEC-ID，且追溯至少一個 REQ-ID |
| ☐ | Issue 包含 feature／test／acceptance（可另含 debug） |
| ☐ | 可取得 requirements／spec／issues 的 Markdown 或 JSON |

**證據（每輪填一列，見下方「三輪紀錄」）：** 錄影連結、截圖路徑、或產物檔路徑。

---

## G-02 — 工程師收得到指派並能開工

**條件：** 指派的工程師能在控制台／GitHub 看到工作項並開工。

| 勾選 | 檢查項 |
|:----:|--------|
| ☐ | Issue 已寫入真實 GitHub（非 dry-run） |
| ☐ | 至少一則 feature／追蹤類 Issue 有 **assignee**（GitHub login） |
| ☐ | 工程師在 GitHub 看得到該 Issue |
| ☐ | 工程師在**控制台**任務面／Issue 列表看得到（或書面說明控制台經 GitHub 同步可見） |
| ☐ | 工程師能 clone 目標倉並開始實作（不要求合併 PR） |

**證據：** Issue URL、assignee login、控制台截圖或見證備註。

**條件：** 範圍／非範圍寫進產物，且標註 AI／分析假設（不可 silently 當成已確認）。
