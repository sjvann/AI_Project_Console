# 願景與買家

**規劃**為主。控制台能力標 **現況**。仲介平台與成交後工作區皆為規劃，不能講成已出貨。

## 一句話

有軟體需求的公司（不限軟體業）與工程師（分析、設計、開發、測試）在同一仲介平台成交；成交後用公司工作區管專案，用本機控制台做工與申報時數。平台抽專案仲介費。加入免費，認證要強。

## 三層產品

| 層 | 狀態 | 給誰 | 誰營運 |
|----|------|------|--------|
| **仲介平台** | 規劃；**下一實作** | 需求公司、獨立工程師 | 我們營運的公開 SaaS |
| **公司工作區** | 規劃；**成交後**才開。現有 Company.* 沿用，改租戶 | 成交後的需求公司管理面 | 預設我們主機上的租戶；自架改後期 |
| **控制台** | 現況 | 任何工程師 | 工程師本機安裝包 |

切割以 [總規格・三層產品](spec.md#三層產品) 與 [仲介平台](marketplace.md) 為準。

## 買家

兩邊都是買家。加入會員不收費；營收來自**成交後的仲介費**。

| 邊 | 誰 | 為什麼來 |
|----|-----|----------|
| 需求方 | 任何有軟體專案的組織：傳統企業、新創、機關、內部 IT、SI | 發布專案與人力資格，找到通過認證的分析／設計／開發／測試；成交後有管理面，不必先養一支正職團隊 |
| 供給方 | 系統分析、系統設計、程式開發、系統測試（個人或工作室） | 找到適合的專案與公司；用自己的控制台做工與申報，不必改用對方的桌面套件 |

**不是首輪：** 要買汎用 ERP／HRIS 的集團人資、要勞務派遣牌照的人力銀行、要把原始碼託管給我們的客戶。

舊文件裡的「10–200 人軟體公司自架營運」改列為：需求方的一種（已有工程團隊的 SI／ISV），在成交後工作區使用管理面；**不是**仲介第一刀的唯一買家。

## 要完成的工作（Jobs to be done）

1. 需求公司用**網頁精靈**寫出專案範圍、人力需求與資格，不必先會 Git。
2. 通過認證的工程師能找到適合自己角色與技能的專案；公司能邀請或接受應徵。
3. 雙方達成協議後拿到合同套件（含保密），平台記下仲介費。
4. 成交後自動有工作區：專案彙整、名冊、工時確認；溝通走 GitHub Issue。
5. 工程師用本機控制台展開作業（進件、堆疊、編譯）並對該工作區接收 API 申報時數。同一人可對多家工作區申報。

## 市場判斷（為什麼現在）

雲端 PM 強在工作單，弱在本機編譯。AI IDE 會改碼，弱在治理。工時工具會計時，弱在合約與外包。人力平台強在履歷，弱在成交後怎麼把需求寫清楚、怎麼真的開工。

**現況**控制台已經補了執行層。缺的不是再賣一套自架給 SI，而是先讓需求方與工程師**成交**，再把已有的公司管理面當成成交後工作區打開。

## 刻意不做

| 不做 | 原因 |
|------|------|
| 取代 Jira／Azure Boards | 任務面以 GitHub Issue 為準 |
| 取代 Cursor／Copilot | Agent 是操作者；控制台是本機真相 |
| 汎用 ERP、總帳、報稅、勞健保申報 | 工作區匯出給既有財務；仲介第一刀只記應收仲介費，不做金流託管 |
| 把客戶原始碼收到我們的雲 | 控制台本機；上傳僅時段與狀態圖 |
| 把控制台做成某家公司的前後台 | 控制台給所有工程師。見 [三層產品](spec.md#三層產品) |
| 勞務派遣、自動媒合、履歷社群 | 本產品是專案承攬仲介，不是 104／派遣公司 |
| 在仲介層重做薪資／毛利／戰情室 | 那是成交後工作區，沿用現有公司平台碼 |

**已翻轉的舊非目標：** 公開 SaaS 多租戶與需求公司自助發布，改為**仲介預設**。客戶自架公司平台改列後期。

## 成功長什麼樣

- Tech Lead 用自己的倉 **90 分鐘**走完控制台（現況）。
- 一組通過認證的需求公司與工程師，走完發布 → 應徵／邀請 → 雙方同意 → 合同產生 → 開工作區 → 控制台申報第一筆工時（規劃，仲介第一刀驗收）。
- 成交後需求公司打開工作區，看得到專案、人、待確認工時，不必問「那個專案怎樣」（規劃，成交後）。
